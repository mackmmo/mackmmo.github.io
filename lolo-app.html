Lolo Climbing App

A geospatial mobile application for exploring climbing routes near Lolo Pass.

GitHub Repo

Project Overview

The Lolo Climbing App is a custom-built geospatial application designed to help climbers discover routes, filter by characteristics, and explore crags in an intuitive way.

Key Features

  • Route filtering by grade, sun exposure, and area
  • Custom spatial database using PostGIS
  • Interactive map-based exploration

Tech Stack

PostgreSQL + PostGIS
Django
JavaScript
Leaflet / Mapping
HTML & CSS

My Role

I designed and implemented the spatial database architecture, including route hierarchies, optimized filtering workflows, and built backend endpoints to serve geospatial data efficiently. Additionally, I assumed the role of project manager in a team of three. As project manager, I was responsible for delegating tasks to develop the frontend and UX/UI.

The Workflow

The Vision

As a rock climber myself and author of A Rockclimber's Guide to Lolo Pass, I wanted to create a mobile application to be used at home and out climbing to both explore Lolo climbing spatially and accurately guide the user to walls and specific routes. As with other climbing guidebook mapping applications. The UI is centered around a map used to pan and zoom to different locations, while also allowing filterable searches that output lists of routes. This filtering is made possible with a PostgreSQL/ postGIS database. The database is set up with four relational tables: Sectors > Areas > Subares > Routes. This structure made the most sense when organizing the routes based on the locations. My Django backend utilizes REST APIs to return endpoints (GeoJSON/JSON).

Sectors

Spatially, each sector is a polygon, with individual areas as multipolygons within it. Sectors do not carry much information besides a "spatial bucket" for areas to live in.

Areas

These multipolygon areas were generated from LiDAR DEMs. The DEMs were processed by first converting to a slope raster. I then masked out all pixels that were not in a range between 60 to 80 degrees. This produced a raster of all clifflines within the Lolo area, which were then converted to polygons. The next step was to manually place a point for each area location. For the next steps, I imported a shapefile for area points and area polygons with CRS 6857 (web mercator). Within the PostgreSQL/postGIS environment, I executed an SQL expression, equivalent to a spatial join in other GIS. This output consisted of multi-polygon features that now belong to an area. To finalize the area table, I imported a csv with area attributes and joined it to the area table on area name. By far, the trickiest table to create as the workflow from raster, to polygon, to multipolygon feature, to PostgreSQL table time instensive.

Subareas

A subarea is a wall or other smaller area within an area. In the schema, some areas do not have subareas since there may only be a single wall for the whole area. It was necessary to subdivide the areas a step further to make my sun aspect logic work. An area my have multiple walls with different aspects. It also create a more organized intuitive way for a user to compartmentalize an area. Geomtries of subareas fall back to the geometry of the area.

Routes

A route lives in the route table and contains various filterable attributes such as grade, type, geometry, and star rating. The geometry of a route falls back onto its subarea and if a subarea does not exists, it's associated area.

Django Backend

I utilized a Django backend and Restful APIs to create Models, Merializers, ListViews, and DetailViews to create endpoints used by front end HTTP requests.
